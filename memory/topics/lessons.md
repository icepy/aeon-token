## NOTE / Robinhood Chain

- **代币合约本身作为 watch 时，`to == watch` 算不出方向。** NOTE 的 watch 地址就是代币合约，所以要按池子判断：`X → PoolManager` 是卖，`PoolManager → X` 是买。按错误逻辑，2026-10-21 14:57Z 那笔 88,744 NOTE 的**买入**会显示成大额流出。多跳路由下同一笔 tx 里 NOTE 会转手 4 次，按"每笔 Transfer"计数会把 1 笔记成 4 笔。详见 [NOTE 笔记](/topics/tokens/note-systems.md)。
- **calldata 解码 ≠ 链上事实。**「30 天线性释放每天 2 万」是从 selector `0x091e7db9` 的 calldata 推出来的；4 小时后 0 笔出账、四个标准 selector 全 revert，证明那只是登记调用。**先看余额与出账，再谈机制。**
- **新钱包 + 固定金额整数 = 先看 gas。** NOTE 团队抛售前会把整数枚转进全新 EOA；该 EOA 无 ETH 时无法卖出，所以"第一笔 ETH 入账"比"转账发生"更接近真实开砸时刻。盯 gas 充值，不要盯转账本身。
- **链上预警有保质期。** 一旦团队把"一次性砸盘"改成"线性释放"，盯转账就失效了 —— 信号还在，但边际价值塌了。判断出货持续性要看**总量与节奏**，不是单笔。
- **owner 自有余额与 timelock 是两条独立供给。** 别只盯 unlock 排程：NOTE owner EOA 不等 10-23 解锁就自行转出了 24 万。
- **Robinhood Chain (4663) 不需要 key。** `rpc.mainnet.chain.robinhood.com` 免密钥即可 `eth_getLogs` 宽区间；GeckoTerminal (`networks/robinhood`) 和 CoinGecko 都能报价。别浪费回合找端点。
- **监控盲区：Path C 只读 ERC-20 logs，看不到 native ETH。** Robinhood 无 key 时 `onchain-monitor` 走 Path C，因此"staging 钱包被充 gas"这类触发器永远不会响，需要额外跑 `eth_getBalance` 轮询。

## 假零与断层

### 「流出」不等于「卖出」：归因到终点之前不要称它为压力

**2026-10-25 踩到的最贵一次误读。** 连续多轮把 CLAIM 主库 24h 流出 **338,594 DEUS** 当成「日滴 338k = 砸盘压力」，还拿它去算砸到 $0.012 要几天。

把 2,244 条 `Transfer` 全部按接收方 `eth_getCode` 分类后真相是：
- **97.8% 流进四个自家导管合约**，且这些合约的合并余额在**涨**（进 331,109 / 净增 +186,619）；
- 导管真正再派出去的只有 **145,228**（**42.9%**，不是 100%）；
- 这 145,228 里 **0** 直接进任何一个 DEUS 池；93,716 走三个已验证 claim→砸盘 EOA，23,756 进了 xDEUS 质押；
- **真正砸向市场的估算 ≈ 75,977/天 = 供应的 0.0087% ≈ $1,318。**

**纪律：一条「流出」要成为「卖压」，必须满足全部三条** —— ① 接收方不是发行方自己的合约；② 该接收方的余额**下降**（不是收了就存着）；③ 终点落在某个池子或最终卖出者手上（不是又进了质押）。**只看第一跳的总额，会把内部搬家读成洪水。**

**快速的重复核验**：对导管群做 `now` 与 `−86400s` 的 `balanceOf` 差。余额**上升** = 在仓库里堆着；余额**下降快于其派发** = 真在往外倒。

### 「连续多轮读数不变」不是「没变化」，是「没落在观察窗里」

**2026-10-25 08:09Z。** `totalSupply` 连续五轮读到同一个数字（−12,373.69 报了两天），于是写下「通缩彻底走平」。本轮建 9 点时间序列后真相是：**07:09Z 之前逐 wei 不变，07:11:49Z 单块跳 +85,828.91**，是史上最大单次增发（前记录 14,413）。**「同一个数字反复出现」在 mint/burn 型变量上只能证明观察点之间没有事件，不能证明没有事件。**

**纪律：任何增量型链上变量（`totalSupply`、`balanceOf`、导管余额）要下「走平/通缩」判断，先取 ≥3 个跨度不同的点（15m / 1h / 6h / 24h / 48h）看形状；单点重复一律只写「本轮未见变化」。** 区块时间戳必须断言（本轮 24h 窗口第一次搜索下界太窄，落回 80,000s 而不是 86,400s，−2.65% 是错的口径，修正后 −3.80%）。

**配套判据**：mint 事件用 `Transfer(from=0x0)` 抓，burn 用 `Transfer(to=0x0)`，且必须跑判别力控制（故意改 1 字符 topic0 应回 0）。本轮控制真 171 / 假 0，证明那 171 条里确实包含这笔。[source: logs/2026-10-25#price-alert]

### 大额 mint 看收款地址的 nonce 与铸前余额，别看金额

**2026-10-25：** 85,829 DEUS 拆给 8 个地址，第一反应是「8 个新钱包在接盘」。查 `eth_getTransactionCount` 后全部 **nonce = 1**，且 8 个地址**铸币前都已有余额**（合计 313,140）；滚动余额 384,051(−30d) → 327,370(−7d) → 398,969(now)。真相相反：**一群存量 dormant 地址，卖了一个月之后被重新充弹。**

**判据：`nonce == 0` 或铸前 `balanceOf == 0` 才是新钱；否则先当作存量地址的仓位调整。** 而且「刚收到」不等于「要卖」—— **8 个地址至今一笔未转出**。分发 ≠ 抛售，和上一条「流出 ≠ 卖出」是同一个病。

### API 的 `h1 = null` 不能被读成 0，也不能被读成「平静」

**2026-10-25：** DexScreener 在深池那对上返回 `priceChange.h1 = null`（5 个 Base 对里 3 个是 null）。若按 0 处理，sharp-move gate 会显示 QUIET —— 但那不是「测到没动」，是**没测量**。

本轮的正确做法：直接问池子。`getReserves()` 的第三个返回值 **`blockTimestampLast` 就是最后一次成交的时间戳** —— 一旦看到它停在 63.9 分钟前，且首尾 `getReserves()` **逐 wei 相同**，就同时证明了「零 swap」和「比值未动」。

**然后还有第二层**：比值没动 ≠ USD mark 没动。本轮 1h 的 **−0.19% 全部来自 VIRTUAL 引腿**（0.627966 → 0.626781）。**一个 USD 计价的涨跌幅永远是「本币腿 × 引腿」两件事，两个都要单独说清楚是哪个在动。**

### 24h 分解的两条腿会重复计数，不能相加

恒定乘积池里，「比值变化 X%」和「DEUS 进池 Y%」是**同一个事件的两种计法**（DEUS 进 ⇔ VIRTUAL 出，比值必随之变）。**只有引腿是独立项，它与池内项是复利关系，不是加法关系。**

2026-10-25 实测：比值 −1.209%、DEUS 进池 +0.610%、VIRTUAL/USD −2.671%，USD mark **−3.848%**（≈ 1.01209 × 1.02671 − 1）。上一轮把三者写成「三分之二是引腿、三分之一是进池」并列相加，口径错了。**报分解时要明说哪两项同源。**

### `-32602` 有两种来源：窗口超限 **和** 自己拼错了 calldata

上面那条讲的是窗口 >1000 块。**2026-10-25 踩到第二种：拼错的 calldata 同样返 `-32602 invalid params`。**

写了个 `pad(addr)` helper 返回**带 `0x` 前缀**的 64 位 hex，调用处又写成 `'0x70a08231' + pad(addr)`，拼出来是 `0x70a082310x<64 hex>` —— **字符串中间多了一个 `0x`**，端点直接判非法参数。症状和「RPC 挂了」一模一样，但换成裸 hex 拼接立刻返回正确余额（escrow 29,150,566.78）。

**纪律**：`pad()` 一类 helper **只返回裸 hex，`0x` 只在 data 字符串开头出现一次**；写个 `0x70a08231` + pad 的自检（长度必须 = 10 + 64）。**看到 `-32602` 先怀疑自己的编码长度，再怀疑端点。**

### `eth_getLogs` 返回 `result: null` 不是"零日志"，是端点拒绝

窗口 1001 块（超出 Tenderly 1000 块上限）时，RPC 回 `{"error":{"code":-32602,...}}`，**没有 `result` 字段**。
若 `jq` 只写 `.result | length`，`null|length` 得到 `0` —— 与"该窗口真无事件"**完全同形**。

2026-10-24 price-alert 首轮就踩了：扫深池 Swap 得 `n:0`，差点报"这一小时池子没成交"；改用 ≤1000 块窗口 + 强制先查 `.error` 后，同一时段实际有 **23 笔 Swap**。

**纪律**：`jq` 取日志数永远写成
```jq
{err:(.error.message//null), n:(if .result then (.result|length) else "NULL" end)}
```
看到 `NULL` 或 `err` 一律重试/缩窗，**不准当 0**。这条是 MEMORY 里"never trust a zero-log window"在**客户端侧**的对应物 —— 之前的假零都怀疑端点或 topic，这次错在自己的解析。

### 第三种假零：Python 里 `except: res = []` 把 `-32602` 吞成"零事件"（2026-10-25 新增）

上面两条是 `jq` 侧的。**Python 侧同样会中招，而且更隐蔽**：包一个 `try/except` 然后 `res = []`，再把失败写进一个没人看的 `errors` 数组。

2026-10-25 price-alert 首扫 escrow 24h 窗（43,296 块）得到 `burns 0 / stakes 0`，**看起来就是"这小时没事件"**；实际是区间超了 1000 块上限，每次调用都 `-32602`。改成 44 个 999 块分片重扫 → **1 burn + 2 stakes**，且与余额差闭合到 wei。

**纪律**：任何"零结果"必须**同时确认失败计数为 0**才能采信。分片扫描的返回结构里必须带 `failed_chunks: []`，并在判定"安静/无事件"之前先断言它是空的。**只看 `len(logs) == 0` 就下结论 = 假零。**

### 「最近一小时」要按时间戳取，不能按 head−1800 块

Base 约 2 秒一块，但**不保证**。2026-10-24 按 `head-1800` 取窗，实际落点是 **100 分钟前**，算出的 h1 与 DexScreener 对不上。
**做法**：二分查找使 `block.timestamp <= head.ts - 3600` 的最大块，并**打印两端时间戳**确认恰好 3600s。

### 解码 Swap 要拿储备差自证，别只信方向

把窗口内全部 Swap 的 `amountIn/amountOut` 加总，与首尾 `getReserves()` 差对账：
- DEUS 腿应**逐 wei 相等**（它是被转移的资产）；
- 报价腿（VIRTUAL/ETH）会差一个**手续费**，残差/输入应等于池子费率。

2026-10-24 实测：DEUS 差 **0.0000**、VIRTUAL 残差 **1.0089%** = Aerodrome classic 费率 → 解码器正确。若两腿都对不上，说明 token0/token1 读反或 topic 拿错。**这是比"看着像买"更硬的验证。**

## 过滤器设计

- **🔴 换词/换词表口径前，先量两个候选口径的 `total_count` 与重叠度，不能只看污染率。** 2026-10-25 `github-radar` 第八轮实测，同一次「缩写→全称」动作在两个词上结果相反：
  - `vla` → `vision language action`：缩写 3,696 命中、污染 **22.0%**；全称 205 命中、污染 **1.4%**、报告级 **47**，且**两口径几乎不重叠**（全称 205 里有 138 个是 `vla` 从没抓到的）。仓库名多为合成词（`smolvla` / `InfraVLA` / `Q-VLA-Forge`），GitHub 按词切分，独立 `vla` token 打不中，而 description 写的正是全称。**污染和漏检同时解决。**
  - `jepa` → `joint embedding predictive`：**654 → 35，损失 94.6%。** JEPA 是固定家族缩写，仓库名一律 `jepa-*`，没人把全称写进 name/description。
  **判据：分界不是「缩写脏不脏」，而是术语在生态里实际怎么被书写 —— 类别通名（VLA）全称是主流，专有家族缩写（JEPA）缩写是主流。** 只看污染率会把两个词推往相反的正确方向。 [source: logs/2026-10-25#github-radar]
- **🔴 共享脚手架簇：owner 黑名单与 `owner≥3仓` 在结构上都抓不到。** 2026-10-25 第八轮，7d 榜首 `AdrienBarrau/jepa-world-model-from-scratch`（30d=46 / 7d=30）是陷阱 —— 同名仓出现在 **8 个不同 owner** 下（第九轮仍剩 4 个），**description 逐字相同、根目录相同、commit message 逐字相同**。每个 owner 只有 1 仓，所以两条规则全部失效。**新增可审计判据：同 repo 名跨 owner ≥3 且 desc 前 80 字符相同 → 判脚手架，一次搜索即可，无需额外 API。** [source: logs/2026-10-25#github-radar]
- **🔴 EXCL 必须同时查仓库名，不能只查 description。** 2026-10-25 第八轮实测 4 个名字含 `awesome`/`website`/`page` 但 desc 不带的全漏，其中 `ishandutta2007/Awesome-Vision-Language-Action-Models`（30d=10）**直接进了报告级**；另有 7 个页面形态（`index.html` + 无代码目录）进报告级。**判据：EXCL 同时查 `repo.split("/")[-1]` 与 description；`*-website`/`*-page`/`*-showcase` 后缀同理。** [source: logs/2026-10-25#github-radar]
- **🔴 `pages` 规则用「体量小」做条件，在巨型静态站上是反的。** 2026-10-25 第七、九轮：加 `not language` 豁免后，`*.github.io` 里 <300KB **但有 language** 的仓被放行（3 个，反向泄露）；第九轮又发现 **19 个页形态幸存、9 个进报告级，最大 304,228KB**（`le-wam/le-wam.github.io` 297MB、`morphact-website` 99MB）。**判据改为「名字像页 / 后缀像页」单条件成立即丢，或改用「根目录无 src/contracts/crates 且 language ∈ {HTML,CSS,JS,TS}」。`size` 与 `language` 都不能单独当豁免。** [source: logs/2026-10-25#github-radar]
- **🔴 已合并 ≠ 已生效：refactor 会基于旧副本把修复静默删掉。** 2026-10-25 `arxiv-radar`：PR #8（10-24 11:20:09Z 合并）给 `CARRIER_MARKET` 追加 8 个词；26 分钟后的 `0e85bfd8`（11:46:07Z，「Refactor term handling」）基于**早于 PR #8 的旧副本**改动，把 8 个词连注释一起删掉，`main` 上退回到 5 词。**实测代价：90 天窗里会丢 1 篇真论文、0 噪声（`2608.13271` 只写 `distributed ledger`/`block creator`/`transaction ordering`），且表现成「零命中」。**
  **判据：`gh pr view --json state,mergedAt` 说 MERGED 只证明合并过；必须对照文件本体（`skills/arxiv-radar/SKILL.md:120`）与 commit 历史。单看 PR 状态会误判已生效，单看文件会误判 PR 没合 —— 两者对不上才定位得到覆盖它的那次 commit。** 另注：本仓库是 shallow clone，`git log` 只有 1 个合成快照提交，**判断 skill 变更必须走 `gh api /commits?path=…`**。 [source: logs/2026-10-25#arxiv-radar]
- **carrier / 领域过滤器必须按簇配，不能全局一套。** 2026-10-24 `arxiv-radar` 实测：一套链上 carrier（`blockchain` / `token` / `validator` …）套在「具身/机器人数据」词上，**90 天窗 20 篇全被丢，20 篇一个链上词都不含**；而少数「幸存」的反而靠同形异义（`token`=GAP tokens、`validator`=validator-passed 环境、`network`=agentic robot network）混进来。**真货全丢、噪声全进 —— 方向是反的。** 症状表现成「零命中」，跟「话题死」无法区分。改法：按词分域给 carrier（`CARRIER_BY_TERM`），90 天窗幸存 0 → 21、ZK 零噪声。**判据：过滤器丢掉的样本要全量抽检，不能只看幸存者 —— 只看幸存者会得到「过滤器工作正常」的完全错误结论。**
- **小众域的过滤器不要"顺手放宽"。** 同一次里试过给 ZK 域加 `proof`/`circuit`/`prover`，会把纯复杂度理论、ZK Proofs of Quantumness、点加硬件加速等 8 条理论/硬件论文捞回来。**同一个放宽动作，在机器人域是纠错、在 ZK 域是引噪** —— 必须逐域验精度，不能统一推。
- **「抽样核查」不能按结果排序取前 N。** 2026-10-25 `github-radar` 实测：skill 自带 audit 对「创建时间最新的 25 个」查 30 天提交，60 天窗下这 25 个全部落在最近两天、全部 ★0 —— **铁律「判真伪只看 commits」在默认实现下永远碰不到 ★≥10 的那 162 个仓。** 症状是审计日志看起来完整（有 commits30d 列、有 stale 标记），但核验对象全是噪声。**任何按排序截断的抽样，都要先问「这个排序跟我要判的属性相关吗」；不相关就换个入口（本轮改成 10 月新建 ★≥5 + 更早 ★≥50，共 120 仓）。**
- **`total_count` 覆盖率连续两轮钉在 32.1% = 窗口化已经到头。** `github-radar` 17 词 × 3 窗，7,551 → 2,426。要真覆盖只能按 `created:` 逐日切片，或换 `sort=updated` 取活跃面。**覆盖率 <50% 的词（本轮 `vla` 7.9% / `world model` 21.4% / `jepa` 44.3%）任何绝对数字都不能引用** —— 这一条已连续两轮成立，不是偶发。

## Watch configuration

- **钱包型 watch 不能用 `eth_getLogs{address: <EOA>}`。** EOA 不发事件，该写法永久返回 0 —— owner EOA / staging / vesting / DEUS escrow 四个 watch 曾长期处于假零。正确形状是在**代币合约**上做 topic 过滤：`[Transfer, null, padded(wallet)]` 收、`[Transfer, padded(wallet)]` 发。
- **xDEUS is ERC-721, not ERC-20** — `decimals()` reverts, `Transfer` carries `tokenId` in `topics[3]`. The ERC-20 topic0 hash still matches, so watch config needs no change.

## 扫 timelock：窗口与 topics 两个坑

1. **窗口别从"最近几天"往回数。** Robinhood 链实测约 34k 块/小时，48h 的排程跨度约 160 万块。2026-10-22 用 `from=94700000` 起扫，完全漏掉 blk 94195015 的 `CallScheduled`，结论一度变成"120 万解锁不存在/已撤销"。正确做法是从**已知排程块**往前推，而不是从当前块往回数。
2. **`eth_getLogs` 不要传 `topics: null`。** 部分节点会返回空数组而不报错，静默变成"没有事件"。要扫全部事件就**省略 topics 字段**，而不是显式传 null。

误判代价很高：这两条任何一条踩中，都会把"明天有 120 万解锁"读成"没有风险"。
